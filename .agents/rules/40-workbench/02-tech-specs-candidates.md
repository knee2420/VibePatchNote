# Workbench: 02.tech_specs_candidates Guidelines

## 1. 목적
`workbench/02.tech_specs_candidates/`는 요구사항(`01.requirements_analysis`)을 기술적으로 구현하기 위해 검토하는 다양한 라이브러리, 프레임워크, 파서 엔진, 알고리즘 등의 **기술 스펙 후보군 및 대안 비교 분석(Technical Candidates & Alternatives) 저장소**입니다.

---

## 2. 역할 구분

| 디렉토리 | 다루는 핵심 질문 | 성격 |
| :--- | :--- | :--- |
| `01.requirements_analysis` | **"무엇을, 왜 만드는가"** | 비즈니스/기능 요구사항 |
| `02.tech_specs_candidates` | **"어떤 기술 후보가 있고, 장단점은 무엇인가"** | 기술 스펙 후보 검토 및 대안 분석 |
| `99.archive` (ADR) | **"최종적으로 무엇을 채택했는가"** | 확정된 아키텍처 의사결정 기록 |

---

## 3. 🚨 작성 및 관리 원칙

### ① 다각도 비교 분석 (Trade-offs Evaluation)
후보 기술을 평가할 때는 다음 기준을 다각도로 분석하여 기록합니다:
- **기능 충족도**: 요구사항의 원자적 기능들을 어디까지 자체 지원하는가
- **아키텍처 적합성**: 확정 기술 스택(React 19, Turborepo, FSD, FastAPI) 및 레이어 규칙과의 조화
- **비기능 요구사항**: 번들 크기, 렌더링 성능, 메모리 오버헤드, 라이선스, 활성 메인테이너 상태

### ② 배제 사유(Rejection Reason) 명시
- 채택되지 않고 탈락한 기술 스펙 후보라도 **"왜 탈락했는지(어떤 제약/결함이 있었는지)"**를 반드시 명시합니다.
- 향후 유사한 기술 검토 시 이미 검증된 비효율적인 선택지를 재조사하는 낭비를 방지합니다.

### ③ PoC(Proof of Concept) 결과 기록
- 필요 시 작은 단위의 프로토타입이나 벤치마크 테스트 결과를 요약 수치(처리 속도, 메모리 점유율 등)와 함께 카드로 정리합니다.
- 복잡한 성능/버그 규명은 `04.measurement`에 위임하되, 기술 도입 전 비교 검토 수치는 본 디렉토리의 후보 카드에 첨부합니다.
