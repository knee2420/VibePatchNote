## 1. 배경 및 문제 정의 (Background & Problem Statement)

### 1.1 배경
VibePatchNote는 문서의 시각적·논리적 구조를 분석하여 Tiptap 와이어프레임 서식으로 복원하는 다단계 복합 Agent 시스템을 갖추고 있다. 이 시스템은 현재의 Antigravity CLI(`agy`)와 Google Direct REST API뿐만 아니라, **향후 `gpt-cli`, `claude-cli`, 에르메스(Hermes) 베이스 오픈소스 모델, 로컬 vLLM/Ollama 등 다양한 CLI 바이너리 및 엔드포인트가 지속적으로 추가·확장되는 멀티 엔진 생태계**를 지향한다.

### 1.2 핵심 문제 (The Bottleneck)
1. **깜깜이(Black Box) 실행과 신뢰성 결여**:
   - 에이전트가 내부적으로 어떤 프롬프트를 조립했는지, 비전 이미지 파일이 실제로 첨부되었는지 텍스트만 들어갔는지, 모델이 Raw 문자열로 무엇을 반환했는지를 브라우저 화면에서 확인할 수 없다.
   - 문제 발생 시 개발자가 매번 터미널을 열고 `apps/api/data/runs/` 디렉터리의 JSON 파일을 직접 열람하거나 CLI 프로세스 로그를 뒤져야만 진실을 파악할 수 있어 디버깅 및 성능 튜닝 사이클이 극도로 지연된다.
2. **이종 런타임(다양한 CLI ↔ REST API ↔ 로컬 서빙 ↔ Fallback) 관측의 사각지대**:
   - LangSmith, Phoenix 등 기성 LLM 관측 툴은 표준 HTTP SDK만을 전제하므로, OS 프로세스(`stdin/stdout` 파이프)로 동작하는 다양한 CLI 도구들(`agy`, `gpt-cli`, `claude-cli`)이나 429 쿼터 초과 시 발동하는 독자적 서킷 브레이커/폴백 상태 머신을 추적하지 못한다.
3. **엔진 확장에 따른 비교 분석 난항**:
   - 새 모델이나 신규 CLI 엔진(예: Hermes 로컬 모델 vs Claude CLI vs Gemini)이 추가될 때마다 "어떤 엔진이 표 인식을 더 잘하는가", "비용과 토큰, 레이턴시는 어떻게 다른가"를 정량적으로 비교할 수 있는 표준화된 관측 창구가 없다.
4. **도메인 시각화의 부재**:
   - 단순 텍스트 로그만으로는 "원본 PDF 기하 격자 대비 추출된 Bounding Box가 얼마나 정확한가", "Tiptap 슬롯이 올바르게 치환되었는가"를 검증할 수 없다.

## 2. 목표 및 원칙 (Goals & Principles)

### 2.1 목표 (Goals)
1. **엔진 비의존적 플러그인 확장성 (Engine-Agnostic Extensibility)**:
   - 특정 벤더나 CLI에 종속되지 않는 범용 관측 구조를 확립한다.
   - 향후 `gpt-cli`, `claude-cli`, 에르메스(Hermes) 로컬 모델 등 **새로운 엔진/하네스가 `BaseLlmHarness` 계약을 따라 추가되면, UI 코드 수정 없이도 자동으로 감지되어 파이프라인 명세, 입출력 트레이스, 벤치마크에 편입**되어야 한다.
2. **완전한 엔지니어링 투명성 확보**: 입력 원본 문서부터 최종 Tiptap 와이어프레임까지, 에이전트 파이프라인의 전 단계를 가감 없이 분해하여 관측한다.
3. **독립적 로컬 런타임 완결성**: 외부 상용 클라우드나 무거운 모니터링 데몬 없이, 현재 모노레포 아키텍처 내부 데이터(`apps/api/data/runs`, `tracer`)만으로 완결되는 전용 Inspector 앱/페이지를 제공한다.
4. **튜닝 피드백 루프 극대화**: 프롬프트 수정, CLI vs API vs 로컬 모델 간 비교, 모델 변경에 따른 성능/토큰/비용 변화를 즉각 계측하고 비교한다.

### 2.2 비목표 (Non-Goals)
- 본 옵저빌리티 시스템은 **철저한 View 전용(Read-Only) 관측 도구**이다. 화면에서 프롬프트 원본 파일을 직접 수정하거나 백엔드 코드를 즉석 패치하는 기능은 포함하지 않는다 (설정 변경은 기존 `llm-settings` 라우팅 패널을 통해서만 수행).
- 실시간 분산 APM(Datadog 등)의 시스템 리소스(CPU/메모리) 모니터링을 대체하지 않는다. 순수 Agent 런타임과 데이터 흐름 추적에 집중한다.

## 3. 상세 요구사항 (Functional Requirements)

### FR-01. 파이프라인 단계별 명세 및 계약 뷰 (Pipeline Spec & Contracts)
- **FR-01-1**: 시스템 내 등록된 모든 파이프라인(`OutlinePipeline`, `ScaffoldReconstructPipeline`)의 정적 구조를 단계별(Stage-by-Stage) 블록 다이어그램으로 시각화해야 한다.
- **FR-01-2**: 각 단계는 명확한 3대 엔지니어링 계약을 표시해야 한다:
  - `Input Contract`: 해당 단계가 요구하는 데이터 타입 및 Pydantic/JSON 스키마 (예: PDF 경로, `context_text`, `json_schema`).
  - `Internal Engine`: 단계 내부를 실행하는 핵심 모듈/함수명 (예: `DocumentContextBuilder.build_context()`, `Harness.run_structured()`).
  - `Output Contract`: 단계 완료 시 산출되어 다음 단계로 전달되는 데이터 규격 (예: `OutlineOutput`, `ScaffoldExtractResult`).

### FR-02. 단계별 중간 실행 값 완결 열람 (Intermediate State Live Inspector)
- **FR-02-1**: 특정 실행 건(`run_id`)을 선택했을 때, 파이프라인 각 단계 사이를 통과한 **실제 런타임 데이터(Intermediate Values)**를 날것 그대로 열람할 수 있어야 한다:
  1. `Input Artifact`: 대상 원본 파일명, 파일 크기, SHA-256 해시값.
  2. `Stage 1 (Context Build)`: PyMuPDF가 추출한 단어 좌표, 표 격자, 미디어 메타 원문 문자열.
  3. `Stage 2 (Prompt Ingest)`: 시스템 지침과 동적 컨텍스트가 결합되어 실제 LLM으로 전송된 최종 프롬프트 전문.
  4. `Stage 3 (LLM Raw Stream)`: 모델(CLI stdout 또는 API HTTP Response)이 반환한 미가공 원문 텍스트.
  5. `Stage 4 (Structured JSON)`: 스키마 파싱 및 보정이 완료된 `OutlineDocument` 트리 데이터.
  6. `Stage 5 (Assembly)`: 슬롯이 바인딩된 최종 Tiptap HTML 및 Markdown 산출물.
- **FR-02-2**: 임의의 두 단계 데이터를 좌우로 나란히 놓고 비교할 수 있는 Side-by-Side 뷰를 제공해야 한다.

### FR-03. 프롬프트 구조 해부도 (Prompt Engineering Anatomy)
- **FR-03-1**: 단일 문자열로 전송된 프롬프트를 구성 모듈별로 역분해하여 계층 트리로 시각화해야 한다:
  - `Layer 1: System Constitution`: `system_instructions.md` (서식 표 분해 원칙, 환각 차단 규칙).
  - `Layer 2: Component Taxonomy`: Header, KV, Table, List, Paragraph, Media 분류 정의문.
  - `Layer 3: Dynamic Injected Context`: 문서 메타, 실측 기하 좌표 데이터.
  - `Layer 4: Output Schema Constraint`: `outline_schema.json` 정의문.
- **FR-03-2**: 각 레이어가 전체 입력 토큰에서 차지하는 바이트 및 토큰 점유율(%)을 계산하여 표시해야 한다.
- **FR-03-3**: 프롬프트 지침이 변경되었을 때, 이전 버전 지침과 현재 지침의 Git 기반 시각적 Diff를 열람할 수 있어야 한다.

### FR-04. 멀티 엔진 & 런타임 환경 SSOT 매트릭스 (Multi-Engine Runtime Matrix)
- **FR-04-1 (엔진 실행 프로토콜 표준 분류)**:
  - 시스템에 연결된 모든 엔진을 다음 3대 실행 프로토콜 유형으로 동적 분류하여 표기해야 한다:
    1. `CLI_SUBPROCESS`: OS 프로세스 기반 (`agy`, `gpt-cli`, `claude-cli` 등 stdin/stdout NDJSON 통신)
    2. `DIRECT_REST_API`: 공식 클라우드 HTTP 엔드포인트 직결 (Google Gemini, OpenAI, Anthropic REST)
    3. `LOCAL_SERVING`: 로컬 추론 엔진 서빙 (Hermes 베이스 vLLM, Ollama, 로컬 소켓/포트)
- **FR-04-2 (동적 프로바이더 카탈로그 탐색)**:
  - `HarnessFactory.providers()` 및 `MODEL_REGISTRY`에 신규 엔진이 등록되면, 별도의 UI 코드 수정 없이도 엔진 목록과 지원 모델 스펙이 자동으로 동기화되어 매트릭스에 노출되어야 한다.
- **FR-04-3 (환경별 파라미터 단일 진실 공급원)**:
  - `바이너리 및 경로`: 각 CLI 바이너리 실존 여부 및 버전, 윈도우 UTF-8 파이프 강제 플래그, `core.longpaths`
  - `자격 증명(Credentials)`: 각 공급자별 API Key 등록/유효성 상태 (마스킹 표기)
  - `스토리지 수명주기 매핑`: `config/`, `data/`, `cache/`, `state/`의 실제 물리 경로 매핑
  - `다단계 라우팅 & Fallback 정책 체인`: 1순위(`agy_cli`) ➔ 2순위(`google_api`) ➔ 3순위(로컬 Hermes 등) 페일오버 체인 시각화
  - `설정 출처 표기`: 출처(`.env`, `settings.json`, 기본 하드코딩) 배지 구분

### FR-05. 워크플로우 카탈로그 및 상태 머신 (Workflow Catalog & State Machine)
- **FR-05-1**: 시스템 내 4대 핵심 워크플로우를 카탈로그 형태로 나열하고 각각의 책임을 명시해야 한다:
  1. `Document Ingestion & Outline Workflow`
  2. `Provider Failover & Fallback Workflow`
  3. `Human-in-the-Loop Approval & Resume Workflow`
  4. `Scaffold Reconstruction & Editor Binding Workflow`
- **FR-05-2**: 각 워크플로우의 상태 전이 머신(State Machine) 다이어그램을 제공해야 한다:
  - 상태 목록: `PENDING` ➔ `RUNNING` ➔ `APPROVAL_WAITING` ➔ `COMMITTED` / `FAILED` / `RECOVERING`.
  - 상태를 전이시키는 유효한 트리거 이벤트와 조건(전이 규칙) 명시.

### FR-06. 프론트 기능 ↔ 워크플로우 추적 매트릭스 (Feature-to-Workflow Traceability)
- **FR-06-1**: 사용자가 화면에서 사용하는 모든 프론트엔드 기능(Feature)과 백엔드 런타임의 연결 경로를 1:1로 매핑하는 매트릭스를 제공해야 한다:
  - UI 버튼/컴포넌트 ➔ 호출 API 엔드포인트 ➔ 구동 워크플로우 ➔ 실행 파이프라인 ➔ 사용 하네스/모델.
- **FR-06-2**: UI에서 오류가 발생했을 때, 해당 기능이 의존하는 백엔드 파이프라인과 하네스를 즉시 파악할 수 있어야 한다.

### FR-07. 장애 진단 및 멀티 엔진 벤치마크 (Diagnostics & Multi-Engine Benchmarking)
- **FR-07-1 (통신 및 오류 로그 진단)**:
  - 각 스텝의 HTTP 상태 코드, CLI 리턴 코드, 소요 시간(ms)을 기록하고 열람할 수 있어야 한다.
  - 429 쿼터 초과 시 발동한 서킷 브레이커 차단 로그 및 남은 쿨다운 타이머를 시각화해야 한다.
  - 실행 실패 시 CLI의 `stderr` 원문과 파이썬 예외 스택 트레이스를 전문 열람할 수 있어야 한다.
- **FR-07-2 (임의 엔진 간 A/B 비교 벤치마크)**:
  - 특정 공급자에 국한되지 않고, 동일한 입력 문서에 대해 **임의의 두 엔진(예: `agy_cli` vs `google_api`, `claude-cli` vs `hermes_local`) 간 실행 결과를 나란히 1:1 비교**할 수 있어야 한다:
    - [소요 시간(Latency)] vs [입력/출력/추론 토큰 수] vs [추출된 아웃라인 수/정확도]
- **FR-07-3 (시각 기하 정렬 검증)**:
  - 원본 PDF 페이지 이미지 위에 추출된 `box_2d` Bounding Box를 오버레이하여 시각적 정렬 오차를 직접 눈으로 검증할 수 있어야 한다.

## 4. 비기능적 요구사항 (Non-Functional Requirements)

- **NFR-01 (불변성 및 무간섭)**: 관측 뷰(Inspector)는 원본 데이터(`apps/api/data/runs`, `artifacts`, `ledger`)를 수정하거나 삭제하지 않는 순수 읽기 전용(Read-Only) 동작이어야 한다.
- **NFR-02 (FSD 아키텍처 준수)**: 프론트엔드 구현 시 `app → pages → widgets → features → entities → shared`의 단방향 의존성 헌법을 엄격히 준수한다.
- **NFR-03 (독립성 및 성능)**: 외부 클라우드 통신이나 무거운 관측 데몬(Docker 등) 없이, 로컬 파일 시스템 및 기존 백엔드 API만으로 1초 이내에 뷰를 로드해야 한다.
