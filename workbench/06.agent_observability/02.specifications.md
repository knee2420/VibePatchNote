## 1. 아키텍처 개요 (Architecture Overview)

본 사양서는 LangSmith/LangGraph의 핵심 아키텍처 패턴을 벤치마킹하여, **OS 서브프로세스 기반 CLI(`agy`, `gpt-cli`, `claude-cli`), 직접 REST API, 로컬 서빙(vLLM/Hermes) 및 복합 Fallback 시나리오**를 통일된 표준 인터페이스로 관측할 수 있도록 정의한다.

```text
[Pipeline Execution]
        │
        ▼
[VibeTracer (Core Span Collector)]
        │
        ├──▶ 1. CLI Process Wrapper (환경변수 주입: VIBE_PARENT_SPAN_ID, VIBE_DOTTED_ORDER)
        ├──▶ 2. HTTP/SDK Adapter (Direct REST API 계측)
        └──▶ 3. Local Serving Adapter (Unix Socket / Localhost HTTP 계측)
        │
        ▼
[Storage Engine (apps/api/data/runs/{run_id}/)]
        ├── ledger.jsonl      (모든 Span 및 Event의 불변 Append-Only 스트림)
        ├── snapshots.json    (각 파이프라인 단계별 Intermediate State 스냅샷)
        └── artifacts/        (입력 PDF 기하 데이터, 프롬프트 원문, Tiptap 산출물)
        │
        ▼
[FastAPI Observability Router (/api/v1/inspector)]
        │
        ▼ (SSE Event Stream / REST JSON)
[React Flow & Tiptap Inspector UI (@vibe/web)]
```

## 2. 통합 Span 데이터 모델 (Unified Span Contract)

LangSmith의 `run-data-format.md` 및 `coding-agent-metadata-contract.md`를 토대로, 우리 시스템에 최적화된 불변 Span 레코드 스키마를 정의한다.

### 2.1 `SpanRecord` 필드 명세

| 필드명 | 타입 | 필수 등급 | 설명 및 예시 |
|---|---|---|---|
| `span_id` | `string (UUIDv7)` | **always** | 시간순 정렬이 가능한 고유 스팬 식별자 |
| `trace_id` | `string (UUIDv7)` | **always** | 최상위 파이프라인 실행 식별자 (`run_id`와 동일) |
| `parent_span_id` | `string \| null` | **always** | 직속 부모 스팬 식별자 (루트일 경우 `null`) |
| `dotted_order` | `string` | **always** | **트리 계층 정렬 키**: `<시작시간>Z<루트ID>.<시작시간>Z<자식ID>` |
| `name` | `string` | **always** | 작업 논리명 (`outline_pipeline`, `build_context`, `llm_attempt`) |
| `span_type` | `enum` | **always** | `pipeline` \| `chain` \| `llm` \| `tool` \| `parser` |
| `status` | `enum` | **always** | `PENDING` \| `RUNNING` \| `SUCCESS` | `FAILED` | `SKIPPED` |
| `start_time` | `string (ISO8601)` | **always** | 실행 시작 시각 (UTC, 나노초 권장) |
| `end_time` | `string \| null` | **where_known** | 실행 종료 시각 |
| `latency_ms` | `float \| null` | **where_known** | 실행 소요 시간 (밀리초 단위) |
| `inputs` | `dict` | **always** | 해당 스팬에 전달된 입력 데이터 (직렬화된 JSON) |
| `outputs` | `dict` | **where_known** | 해당 스팬이 산출한 출력 데이터 |
| `error` | `dict \| null` | **where_known** | 실패 시 `{ code, message, stack_trace, stderr }` |
| `metadata` | `dict` | **always** | [코딩 에이전트 메타데이터 규약](#22-코딩-에이전트-메타데이터-규약) |
| `usage` | `dict` | **where_known** | `{ prompt_tokens, completion_tokens, total_tokens, cost }` |

### 2.2 코딩 에이전트 메타데이터 규약 (`metadata`)

CLI 및 이종 엔진을 투명하게 식별하기 위해 모든 Span은 다음 메타데이터를 포함한다:

```json
{
  "agent_runtime": "agy-cli 2.0",
  "execution_protocol": "CLI_SUBPROCESS",
  "provider": "agy_cli",
  "model_name": "gemini-3.5-flash",
  "thread_id": "doc_outline_01",
  "git_branch": "main",
  "git_commit_sha": "a1b2c3d...",
  "working_directory": "c:/AI_Projects/WebNovelAssistant/VibePatchNote",
  "cli_command": ["agy", "agent", "run", "--model", "gemini-3.5-flash"],
  "exit_code": 0
}
```

## 3. 계층형 트리 복원 알고리즘 (`dotted_order`)

LangSmith의 정렬 방식을 차용하여, DB 조인 없이 단일 문자열 비교만으로 완전한 부모-자식 트리와 깊이(Depth)를 재구성한다.

### 3.1 Dotted Order 생성 규칙
1. **루트 스팬**:
   `dotted_order = "{start_time_iso}Z{span_id}"`
2. **자식 스팬**:
   `dotted_order = "{parent.dotted_order}.{start_time_iso}Z{span_id}"`

### 3.2 트리 복원 알고리즘 (Frontend / Ingestion)
```typescript
// ledger.jsonl의 Span 리스트를 단순히 dotted_order로 오름차순 정렬하면
// 자동으로 시간순 + 깊이순 트리 구조가 완성됨.
spans.sort((a, b) => a.dotted_order.localeCompare(b.dotted_order));

// 각 Span의 깊이(Depth) 계산
const depth = span.dotted_order.split('.').length - 1;
```

## 4. CLI 서브프로세스 추적 프로토콜 (CLI Tracing Protocol)

`trace-claude-code.md`의 환경변수 상속 메커니즘을 채택하여, OS 프로세스 레벨에서 실행되는 CLI 도구(`agy`, `claude-cli`, `gpt-cli`)를 파이프라인의 자식 스팬으로 결합한다.

### 4.1 백엔드 환경변수 주입 규격
백엔드(`CliAdapter` 또는 `BaseLlmHarness`)가 `subprocess.Popen`을 호출할 때 다음 환경변수를 하위 프로세스에 자동 주입한다:

```python
env = {
    **os.environ,
    "VIBE_TRACE_ID": current_span.trace_id,
    "VIBE_PARENT_SPAN_ID": current_span.span_id,
    "VIBE_PARENT_DOTTED_ORDER": current_span.dotted_order,
    "VIBE_AGENT_RUNTIME": "agy-cli",
    "PYTHONIOENCODING": "utf-8",
    "PYTHONUTF8": "1",
}
```

### 4.2 CLI I/O 캡처 및 계측 생명주기
1. **STDOUT 파이프 감시**:
   - CLI가 출력하는 라인을 실시간으로 스트리밍 읽기.
   - NDJSON 이벤트 스트림(`{"type": "token", "delta": "..."}`)이 감지되면 `on_llm_stream` 이벤트로 백엔드 Tracer에 중계.
2. **STDERR 버퍼링**:
   - 비정상 출력 및 경고 문구를 별도 메모리 버퍼에 축적.
3. **종료 코드(`returncode`) 검증**:
   - `returncode != 0`인 경우:
     - `status = FAILED`
     - `error = { "exit_code": returncode, "stderr": stderr_buffer }`
     - Fallback 시퀀스 즉각 발동.

## 5. Model Fallback 추적 모델 (Fallback Attempt Model)

`llm-gateway-fallbacks.md`를 벤치마킹하여, 다단계 재시도 및 프로바이더 치환 과정을 부모 `chain`과 자식 `llm` 시도들로 완벽하게 구조화한다.

### 5.1 Fallback 트리 구조 표준

```text
[Pipeline] Document Outline Pipeline (chain)
    │
    └── [Stage 3] LLM Structure Generation (chain)
            ├── [Attempt 1] agy_cli:gemini-3.5-flash (llm)
            │       ├── Status: FAILED
            │       ├── Latency: 12,040ms
            │       └── Error: { exit_code: 1, reason: "CLI_PROCESS_TIMEOUT" }
            │
            ├── [Attempt 2] google_api:gemini-3.5-flash (llm)
            │       ├── Status: FAILED
            │       ├── Latency: 320ms
            │       └── Error: { http_status: 429, reason: "RESOURCE_EXHAUSTED" }
            │
            └── [Attempt 3] local_serving:gemma-4-31b (llm)
                    ├── Status: SUCCESS
                    ├── Latency: 1,840ms
                    ├── Usage: { prompt_tokens: 1820, completion_tokens: 430 }
                    └── Output: { "raw_text": "..." }
```

### 5.2 부모 스팬의 집계 메트릭 (`aggregated_metrics`)
Fallback 상위 스팬(`LLM Structure Generation`)은 모든 시도의 메트릭을 집계하여 기록한다:
* `total_attempts`: 3
* `final_status`: `SUCCESS`
* `total_latency_ms`: 14,200ms (12,040 + 320 + 1,840)
* `fallback_path`: `["agy_cli", "google_api", "local_serving"]`

## 7. 이벤트 스트리밍 프로토콜 (SSE Lifecycle Events)

LangGraph `event-streaming.md`를 벤치마킹하여, 백엔드 엔진이 프론트엔드 Inspector UI로 전송하는 실시간 SSE 이벤트 규격을 정의한다.

| 이벤트명 (`event`) | 페이로드 (`data`) 주요 내용 | 설명 |
|---|---|---|
| `span_start` | `{ span_id, parent_span_id, dotted_order, name, span_type, inputs }` | 새로운 스팬 시작 알림 |
| `llm_chunk` | `{ span_id, delta, index }` | 모델 출력 토큰 실시간 스트리밍 |
| `span_end` | `{ span_id, outputs, latency_ms, usage, status }` | 스팬 정상 완료 알림 |
| `span_error` | `{ span_id, error, fallback_triggered }` | 스팬 오류 및 폴백 트리거 알림 |
| `state_checkpoint` | `{ stage_id, state_payload }` | 단계별 중간 상태 스냅샷 갱신 알림 |
| `approval_waiting` | `{ run_id, checkpoint_id, preview_data }` | 사용자 승인 대기 상태 진입 알림 |

## 8. 데이터 수명주기 등급 및 디렉터리 배치 (Storage Tiering)

모노레포 정본 헌법([`60-data`](../../.agents/rules/60-data/rule.md))에 따라 관측 데이터를 수명주기 등급별로 엄격히 배치한다:

```text
apps/api/
  └── data/
        └── runs/
              └── {run_id}/                       # [등급 2: 원본·산출물 - 보존 대상]
                    ├── ledger.jsonl               # 전체 Span 및 이벤트 불변 원장
                    ├── snapshots.json             # 단계별 중간 상태 스냅샷
                    └── artifacts/                 # 원본 문서, 렌더링 이미지, 추출 JSON
```

- **불변성 보장**: `ledger.jsonl`은 오직 Append-Only로만 작성되며, 과거 라인은 일체 수정하지 않는다.
- **조회 성능 최적화**: 프론트엔드 최초 로드 시에는 `snapshots.json` 메타데이터만 1회 페치하고, 상세 로그 트리 요청 시 `ledger.jsonl`을 스트리밍 파싱하여 렌더링한다.
